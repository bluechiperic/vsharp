V# for C# developers

Your tests try the inputs you thought of. V# tries all of them.

V# is a .NET language whose compiler proves that each function keeps its contract, for every possible input, before it emits any IL. When it can't, it hands you the input that breaks it.

This primer maps what you already know from C# onto V#, then spends most of its time on the part C# doesn't have: verification.

A pricing helper in C#, with the tests a careful reviewer would ask for.

public static decimal Discounted(decimal price, decimal percent)
    => price - price * percent / 100m;

1What V# is

V# compiles to IL, like C#. A V# module becomes an ordinary assembly, Pricing.dll, that a C# project references and calls like any other library. Records become sealed classes with properties, interfaces become CLR interfaces, and async functions return Task<T>.

What's different is the compiler's job. Next to its signature, each V# function carries a contract: what it requires from callers and what it promises in return. Before generating code, vsharpc turns every promise, every array index, every division and every loop into a logical question, and asks the Z3 solver to find an input that breaks it. When no such input exists, the obligation is proved. When one does, compilation stops and you get that input as a counterexample.

Nothing unproved compiles. A Pricing.dll that exists has met every one of its contracts for every input.

V# is meant for the decision-making core of an application: pricing, eligibility, scheduling rules, authorization limits, moving money. The C# around it keeps doing what C# does well: controllers, data access, logging, dependency injection.

The rules that will feel strange

Each of these exists so that the program you read is exactly the program that gets proved.

  • Every statement starts with a keyword: let, var, set, if, for, while, match, return, do, assert. There are no semicolons, and a malformed line can't swallow its neighbours. Assignment is set x = e, so = is never confused with ==.
  • Names are unique within a function. There's no shadowing, so a name means one thing everywhere in the function.
  • Named arguments are required when two parameters share a type. discounted(price: p, percent: c) can't be written with the arguments swapped.
  • Values are immutable. Records, arrays, classes and unions never change after construction; only local vars do. With no aliasing, the verifier never has to wonder who else changed your data.
  • There's no null. Absence is Option, and every match must handle every case.
  • Side effects are declared. A function that prints says effects io; one that awaits says effects async. Without effects, a function is pure and can appear inside contracts.
  • Everything terminates. for loops are bounded, and each while loop and recursive function states a measure that shrinks.

3Contracts: requires and ensures

A contract has two sides. requires is what the caller must guarantee. ensures is what the function guarantees back, with result naming the return value. Unlike a guard clause or Debug.Assert, neither is checked against the inputs that happen to arrive at run time. Both are proved for all inputs at compile time.

Back to the discount from the top of the page. The counterexample said a percentage over 100 breaks the promise. The fix isn't in the arithmetic. The function needs a precondition saying which percentages make sense:

The caller has two options: guard the call, or push the requirement further up with its own requires. Here a guard makes sense, and the caller states its own promise:

This is the everyday rhythm of writing V#, and the reason edits stay local. Each function is checked only against the contracts of what it calls, never their bodies. Change the body of discounted and only discounted is re-proved. Change its contract and the compiler lists exactly the call sites that no longer hold.

4Refinement types

A refinement type is a base type plus a rule that every value must satisfy: type Weight = Int where self > 0. At run time it's just a long. At compile time the verifier proves the rule wherever a value flows into the type (an argument, a field, a return), and assumes it wherever one is read. You get the benefit of a validated value object without writing the class, the factory or the checks.

That assumption is what lets kilos be proved. Here is the version most people write first:

The proof of result >= 1 uses grams > 0, which the Weight type guarantees. With a plain Int parameter, grams = 0 would be the counterexample.

Refinements carry their rules into records too. In a banking example, type Money = Int where self >= 0 on every account balance means no code anywhere can build an account with a negative balance. 5Loops: invariants and termination

The verifier can't run a loop for every possible number of iterations, so you state what stays true on each pass: a loop invariant. The verifier proves it holds on entry and survives every iteration, then reasons about everything after the loop from the invariant alone. A decreases measure, a non-negative number that shrinks on each pass, proves the loop ends.

Binary search is the classic place where everyone writes an off-by-one. Here's a version that verifies against a full specification: if it returns an index, the key is there, and if it returns -1, the key is nowhere in the array.

Change one character, writing set hi = mid - 1 on the highlighted line, and the bounds no longer mean what the invariants say:

The invariant must hold again after every iteration. The counterexample shows values at the end of one iteration.

A one-element array whose element is larger than the key drives hi to -1. The same edit also breaks the third invariant, and that is the more dangerous bug: in a larger array, the element at mid - 1 drops out of the search, so when it happens to be the key, the function returns -1. A test only catches that if it puts the key in exactly the right place.

Termination

Code that never returns is a bug that tests usually find as a hung build agent. V# rejects it at compile time:

Termination matters to more than build agents. A recursive function's contract is assumed at its own recursive calls, and that is only sound if the recursion ends. Without the check, fn bad(x: Int) -> Int ensures result == bad(x) + 1 would "prove" anything.

7Classes, interfaces and invariants

V# classes are immutable records with methods and invariants: rules that every value of the class satisfies. Because a value can't change after it's built, an invariant proved at construction holds forever. Every method, every caller and every collection of the class can rely on it without re-checking.

Interface methods carry contracts too. Each implementation must meet the ensures it inherits, which is what makes it safe for code to depend on the interface rather than the class.

In the assembly, Range is a public sealed class Range : Sized, and its constructor checks the invariant at run time, so C# code can't build an invalid one either.

8Exceptions as part of the contract

In C#, the exceptions a method can throw are documentation at best. In V#, they're part of the contract, together with the condition under which each one happens: throws E when cond. Every exception is either caught or declared, and the verifier proves the conditions.

A caller that rules out only one of the conditions is told which exception can still escape, and on which input:

RefutedTN3017'Short' might escape 'careless': !frozen && amount > balance might hold here
balance
0
amount
1

The callee throws 'Short' only when its 'when' condition holds. Prove it false here (a guard or a precondition), catch 'Short', or declare 'throws Short'.

The condition binds the thrower too. A function that promises throws Frozen when x > 10 but throws when x > 5 is caught with x = 6. Inside a catch, the verifier knows the condition that caused the throw. That's how a function that catches Frozen and Overdrawn can prove Err(e) => a.frozen || amount > a.balance.

In the assembly, Overdrawn is a sealed class deriving from System.Exception, with balance and amount properties and the message Overdrawn(balance: 100, amount: 500). C# catches it like any other exception, including from a faulted Task.

9How the proof works

There's no magic and no annotation-driven test generation. For each function, vsharpc does this:

  1. It parses and type-checks the module, including effects, exhaustiveness and the routing of every exception.
  2. It executes each function symbolically. Instead of concrete values, variables hold logical terms, and each branch adds a fact to the path. Paths merge after an if, so cost grows linearly with the number of branches.
  3. Each obligation becomes one query to Z3, the SMT solver from Microsoft Research: "find a state that satisfies everything known here but violates this." If none exists, the obligation is proved and becomes a known fact. If one exists, the solver's model is your counterexample.
  4. Calls are replaced by the callee's contract and loops by their invariants, so each function is proved on its own.
  5. Only when every obligation is discharged does the emitter write IL. The class gets [Verified("vsharpc")], and each method carries its contract as [Contract(...)] attributes.

Two consequences are worth internalizing. A counterexample after a loop is relative to the invariant: if it shows a state the program can't really reach, the invariant is too weak, not the code wrong. And the same program gives the same answer every time, because quantifiers are only instantiated through explicit triggers and contracts are unfolded one level.

What a proof doesn't cover

A proof is only as good as what it was asked to prove. Three limits matter in practice:

  • A weak contract is easy to satisfy. ensures match result { Ok(m) => ..., Err(e) => true } lets a function reject every request and still verify. When you review V# code, review the contract first: ask what a wrong implementation could do and still pass.
  • Some things are trusted, not proved. These include the contracts of extern functions that bind .NET methods, C# implementations and mocks of V# interfaces, the Z3 solver itself, and the compiler's code generator.
  • Some models are approximate. Decimal is reasoned about as an exact real number, so a proof about x / 3 * 3 describes exact arithmetic, not decimal rounding. Culture-sensitive string functions are described only partially. Run-time stops (overflow outside total mode, stack exhaustion, out of memory) end the program rather than return a wrong answer.

For the advanced cases there's more: spec fn for mathematical definitions, lemma fn for reusable proofs, ghost variables that exist only for the proof, and quantifiers over whole types. The language specification covers them.

10Calling V# from C#

Reference the assembly and call it. Names appear exactly as declared, records are classes with get-only properties, and unions are an abstract base with a sealed class per case.

That ContractViolationException is the important part. V# callers proved the precondition at compile time; a C# caller didn't. So every public method whose preconditions or refined parameters can run at run time is compiled twice. A public wrapper checks them and throws on a violation, and an internal body is called directly by V# code at no cost. The guarantee holds at the boundary, not just inside V#.

  • Dependency injection and mocks. Register a V# class as the implementation of a V# interface, or mock the interface in tests (the compiler's own tests use DispatchProxy). A mock is trusted to keep the interface's contract.
  • Serialization. Records have structural equality and serialize with System.Text.Json as is. .NET attributes such as @JsonPropertyName("id") pass through.
  • Async. A function with effects async is a Task<T>-returning method, so C# awaits it.

11Writing V# with an AI

V# was designed for a workflow where a person writes or reviews the contract and a model writes the body, with the verifier deciding when it's done. Three tools make that loop work.

Typed holes. Write ?name where an expression is still missing. Compilation stops and reports what the hole must satisfy:

HoleTN4001hole ?kilos has type Int
in scope: grams: Weight
must satisfy: postcondition of 'kilos' might not hold: result >= 1
must satisfy: postcondition of 'kilos' might not hold: result * 1000 >= grams

Replace the hole with an expression of this type that meets the obligations listed.

Diagnostics as data. With --json, every error has a stable code, a span, a hint and the counterexample as structured values, so a model can repair code without parsing prose. This is the hero example's diagnostic, with the hint left out:

{
  "code": "TN3001",
  "severity": "error",
  "message": "postcondition of 'discounted' might not hold: 0m <= result && result <= price",
  "file": "out/primer/hero.vs",
  "line": 7, "col": 3, "endLine": 7, "endCol": 40,
  "status": "refuted",
  "counterexample": { "price": "1m", "percent": "101m", "result": "-0.01m" }
}

Signatures without bodies. vsharpc sig prints every type, signature and contract in a module: everything a caller may rely on, at a fraction of the size. Because verification is modular, that's all a model needs in context to write a correct caller. vsharpc explain TN3017 explains any code with an example fix.

Other choices serve the same goal: one way to say each thing, required named arguments, no shadowing, and one canonical format (vsharpc fmt). Generated code has fewer places to go subtly wrong, and a diff shows only real changes.

12Where it fits

V# works best as a verified core inside a C# application. `samples/scheduling` is a three-file V# module for recurrence, appointment status, and authorization limits.

Write it in V#Keep it in C#
Pricing, fees, discounts, tax rulesControllers and HTTP plumbing
Eligibility and authorization limitsEntity Framework and data access
Scheduling and calendar rulesLogging, configuration, DI setup
State transitions and status logicMutable object graphs and class inheritance
Money movement and ledger invariantsConcurrency (Task.WhenAll), cancellation, UI

There are also current limits. Classes are sealed and immutable, and there's no inheritance between classes. Async is sequential, with await as a statement. Exceptions have no finally. An extern binds static .NET methods over simple types. The implementation status lists them all.
